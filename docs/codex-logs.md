# Codex実行ログ

Codexの実行ログの提出または分析を求められた場合の扱いを定める。

## 基本方針

- 提出・分析には、対象となるCodexの標準session / rolloutなど、既に記録されている情報を使用する。
- 目的に必要な情報が不足する場合は、その内容と分析への影響を示す。
- 追加計測は、不足する情報を取得するための個別の検証として扱う。

作業方法の改善を目的とする場合は、改善候補を特定し、次の検証を設計できるかを、情報の十分性を判断する基準とする。

## 取得する情報

要求された目的に応じて、標準ログから次のような情報を取得する。

- モデル応答とその時刻。
- input tokens。
- cached input tokens。
- cache write input tokens。
- output tokens。
- reasoning output tokens。
- toolやcommandの種類と実行順序。
- toolやcommandの呼び出し回数。
- 開始・終了時刻や実行時間。
- exit codeや実行結果。
- failure、timeout、cancellation、retryなど、ログから確認できる実行上の出来事。

## 集計

- 回数・時間・モデル使用量は、何を数え、どの記録を集計した値か分かる形で示す。
- 応答ごとの値と累積値、外側の呼び出しとその内部操作など、同じ実行を表す記録を重複して集計しない。
- toolとtokenを一対一に対応付けられない場合は、無理に配賦しない。

`uncached input` が必要な場合は、取得した値から次のように算出する。

```text
uncached input = input tokens - cached input tokens
```

## 事実と推定

標準ログから直接確認できる情報と、そこから推定した内容を区別する。

- toolの実行時刻やdurationは、ログに記録されていれば事実として扱える。
- 明示的な工程記録がない状態で、調査・設計検討・実装・検証・ドキュメント更新などの意味上の工程を特定する場合は、推定であることを区別する。
- ログだけでは確認できない原因や判断理由を断定しない。

## 提出

要求された目的に応じて、判断に必要な情報を整理して提示する。

例えば作業方法を分析する場合は、使用した手段、回数、時間、モデル使用量、失敗や再試行など、目的に関係する事実をまとめる。

- raw logをそのまま大量に提示することを標準としない。
- 必要性や効率をログの事実そのものとして扱わない。
- 分析結果から比較する価値のある仮説を立てることはできるが、その妥当性を確認する必要がある場合は別途検証する。
