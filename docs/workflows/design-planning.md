# Design Planning

一定規模以上の新機能や構造変更を、実装前に整理するための方針。

小さく局所的で、後から容易に変更できる修正には原則として使わない。

## 方針

- 現在の実装をGitHubから確認してから検討する。
- ユーザーがGitHubより新しいコードや変更内容を提示している場合は、そちらを優先する。
- 設計結果に影響する未確定事項は、推測で埋めず先に確認する。
- 容易に変更できる軽微な事項は、必要に応じて判断してよい。
- 有力な案が複数ある場合のみ比較する。比較のためだけに代替案を作らない。
- 設計では、責務、依存関係、処理やデータの流れを明確にする。
- 変更範囲、主なリスク、検証方法まで確認する。
- 重要な設計は、ユーザーが理解できる形で説明してから実装計画に進む。

## 進め方

1. 関連するコード、Scene、Resource、既存ドキュメントを確認する。
2. 要求と制約を整理する。
3. 設計に影響する未確定事項を確認する。
4. 必要なら有力な設計案を比較する。
5. 採用する設計と理由を決める。
6. 影響範囲、リスク、検証方法を整理する。
7. 必要に応じて `system-understanding.md` の方針で設計を説明する。
8. Codexへ渡せる実装計画にまとめる。

## 実装計画

実装計画では、少なくとも次を明確にする。

- 何を変更するか
- 各要素が何を担当するか
- 主な依存関係や処理の流れ
- 変更の順序
- 影響範囲
- 検証方法

行単位の変更や、設計上不要な実装詳細までは固定しない。
