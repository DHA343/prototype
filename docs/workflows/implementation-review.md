# Implementation Review

実装済みの変更が、要求と設計に対して正しく実装されているかを確認する。

コード全体の要約ではなく、修正すべき問題、設計からの逸脱、検証不足を見つけることを目的とする。

## 確認すること

優先度の高い順に確認する。

1. 要求を満たしているか
2. 確定した設計と一致しているか
3. バグ、回帰、エッジケースの問題がないか
4. 責務や依存関係が不自然になっていないか
5. 要求と無関係な変更や不要な複雑化がないか
6. Godot固有の問題がないか
7. 必要な実行確認やテストが不足していないか

レビューでは、要求、設計・実装計画、現在のコードを照合する。
ユーザーがGitHubより新しい変更内容を提示している場合は、そちらを優先する。

## Severity

### Critical

承認できない重大な問題。

- クラッシュやデータ破損
- 主要機能が成立しない
- 広範囲な回帰
- 要求や基本設計と根本的に矛盾している

### Major

修正が必要な実質的な問題。

- 要求の一部を満たしていない
- 重要な責務や依存関係が崩れている
- 通常利用で発生し得るバグ
- 将来の変更を明確に難しくする構造
- 重要な検証が不足している

### Minor

影響が限定された改善点。

- 低リスクなエッジケース
- 小さな保守性や可読性の問題
- すぐに障害にはならないが改善価値がある点

単なる好みやスタイル差を、不必要に重大な問題として扱わない。

## 指摘の書き方

問題がある箇所だけを、重要度順に整理する。

各指摘には次を含める。

- Severity
- Location
- Problem
- Why
- Recommended Action

問題がない箇所を大量に列挙しない。

最後に、必要に応じて次のいずれかを示す。

- **Approve**: 重大な問題は見つからない
- **Needs Changes**: 修正すべき問題がある
- **Reconsider Design**: 実装修正だけでは不十分で、設計自体の再検討が必要
