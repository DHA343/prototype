# ドキュメントの運用

ドキュメントの参照と、設計ドキュメント・バックログの作成・更新について定める。

## 参照

作業前に、作業内容に対応するドキュメントを参照する。

| ドキュメント | 内容 | 参照条件 |
| --- | --- | --- |
| [design/](design/) | 現在の設計と、その理解・変更に必要な情報 | 関連する機能や仕組みを調査・変更する場合 |
| [backlog.md](backlog.md) | 今後必要な作業 | バックログを確認・更新する場合 |
| [codex-logs.md](codex-logs.md) | Codex実行ログの提出・分析手順 | ログの提出・分析を求められた場合 |
| [gdscript.md](gdscript.md) | GDScriptの実装規則 | GDScript関連の作業を行う場合 |
| [shader.md](shader.md) | Godot Shader Languageの実装規則 | Shader関連の作業を行う場合 |
| [godot-ai.md](godot-ai.md) | Godot AIの操作規則 | Godot AIを使用する場合 |

設計ドキュメントは、design/配下のファイル名とディレクトリ構造から探す。

## 基本原則

- 継続して必要な知識や規則は、内容に対応するドキュメントへ反映し、作業記録への参照だけで済ませない。
- 設計情報は設計ドキュメントにまとめ、バックログから必要な箇所を参照する。
- 将来に関する情報でも、変更時に守る前提や考慮事項は設計ドキュメントに記録する。
- 設計ドキュメントとバックログは、話題を表す見出しと箇条書きの階層で整理する。
    - 内容の分類や状態を示す定型ラベルは設けない。

## 設計

### 記録対象

現在成立している設計と、その理解・変更に必要な情報を記録する。

- 設計判断の理由。
- 判断に影響した制約や前提。
- 今後の判断にも関係する確認結果。
- 採用案を理解するうえで意味のある棄却案。
- 将来変更・拡張するときに守る前提や考慮事項。

コードや設定を確認すれば直接分かる内容は、必要がなければ重複して記録しない。

### 構成

- 機能や仕組みごとに、関連する設計情報を一つのドキュメントにまとめる。
- 独立して探したり参照したりする必要が継続的に生じた部分だけを、別のドキュメントへ分ける。

### 更新

- 設計変更に合わせて、対応するドキュメントを更新する。
- 現在の設計を理解・変更するために不要になった記述は削除する。

## バックログ

### 記録対象

現在の設計や実装にはまだ反映されておらず、今後行う必要がある対応を、具体的な行為として記録する。

### 構成

- 今後必要な作業はbacklog.mdにまとめる。
- 対象となる機能や仕組みごとに見出しを設ける。
- 補足は各項目の下に箇条書きで記載する。

### 更新

- 完了時に残すべき設計上の知識が得られた場合は、該当する設計ドキュメントへ反映する。
- 完了した項目は削除する。

## 記録先の例

セーブを題材にした仮の例。

- 設計ドキュメント: 保存タイミングを追加する場合も、保存内容と再開地点を一致させる。
- バックログ: ステージクリア時にも自動保存する。
