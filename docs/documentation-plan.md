# ドキュメント管理の改善案

この文書は、ドキュメントの構成と運用を変更する前の提案書です。予定するファイル、内容、作成・整理の手順を示します。ここに記載した構成や指示は、まだプロジェクトの管理ルールに適用していません。

設計の説明は話題ごとに集約し、作業直後の確認資料は作業ごとの一時フォルダにまとめる案です。構成を確認する場合は「2」、文書の具体的な中身は「5・6」、AI向けの運用指示は「7」を参照してください。

## 1. 改善したいこと

- 実装を読んでも分からない判断理由や、重要な試行から得た知見を、後の変更に使える形で残す。
- 人が話題から情報を探せるようにし、現在の選択、理由、残っている問題を見分けやすくする。
- 作業直後の確認に必要な情報と、その後も使う情報の保存先を分ける。
- 文書や時間記録を作る作業自体が膨らまないようにする。
- 同じ情報を複数の場所で管理せず、更新する場所を明確にする。

既存の仕様書の構成を前提にせず、以下の集約案を検討します。

## 2. 予定するファイル構成

パスはプロジェクトルートを基準にしています。以下のファイルを一度にすべて作る計画ではありません。

| 配置 | 役割 | 作るタイミング |
|---|---|---|
| `docs/documentation.md` | 人とAIが共通で使う、文書の作成・更新・整理のルール | 運用を適用するとき |
| `docs/.gdignore` | 文書用の画像などをGodotのインポート対象から除外する空のファイル | `docs/` に画像などの資料を保存するとき |
| `docs/design/README.md` | 話題と文書の対応を示す短い案内 | 複数の文書から参照先を探す必要が出たとき |
| `docs/design/<topic>.md` | 話題ごとの設計の説明 | 継続して使う判断や知見があるとき |
| `docs/design/<topic>/<subtopic>.md` | 独立して読む必要がある詳しい説明 | 一つの文書から必要な部分を分割するとき |
| `docs/design/<topic>/artifacts/` | 後の比較や判断でも使う画像・測定結果 | 元の証拠を残す必要があるとき |
| `docs/templates/work_report.md` | 一時的な作業報告のひな型 | 運用を適用するとき |
| `_temp/work-reports/YYYY-MM-DD_<topic>/report.md` | 作業結果、直後の確認事項、作業時間、整理状況 | 実装作業が完了したとき |
| `_temp/work-reports/YYYY-MM-DD_<topic>/artifacts/` | その作業の比較画像や検証資料 | 作業中に必要になったとき |

### 文書を分ける単位

- 設計の説明は `docs/design/` に集約する。コードの各フォルダに設計文書を機械的に配置しない。
- コードのフォルダ構造をそのまま写さず、「CRT mask」「画面の拡大・縮小」など、読む人が探す話題で分ける。
- 最初は一つの話題を一つのファイルにまとめる。個々の判断ごとにファイルを増やさない。
- 長くなっただけで分割せず、独立して読む・更新する意味がある部分を分ける。
- 必要な場合は関連コードへのリンクを置き、適用先を分かるようにする。コードから分かる設定値や処理の一覧は重複して書かない。

### 現行ルールとの違い

現在の `AGENTS.md` は、作業報告を `_temp/work-reports/<作業名>.md` に保存するよう指定しています。本案では、報告と関連資料を作業ごとのフォルダにまとめます。日付はJSTを使います。

適用時には `AGENTS.md` の保存先と参照先を更新する必要があります。詳細な管理ルールは `docs/documentation.md` に置き、`AGENTS.md` にはその参照を置く案です。現在の `_temp/` は既にGitの管理対象から除外されています。

`docs/` はゲーム実行用のリソースを置かない領域とします。空の `.gdignore` によって、その配下の資料をGodotのインポート対象から除外できます。[Godotの公式説明](https://docs.godotengine.org/en/stable/tutorials/best_practices/project_organization.html#ignoring-specific-folders)

### Gitで管理する範囲

- 設計の説明、管理ルール、ひな型、再利用する証拠はGitで管理する。実装に伴って内容が変わる場合は、実装と併せて更新する。
- `_temp/` の報告・資料はGitで管理しない。
- 一時資料のうち後でも必要なものだけを残す領域へ移す。画像やログをまとめて保存し直す運用にはしない。

## 3. 何を残すか

設計の説明に残すのは、後の変更・再検討・調査に使える情報です。

| 残す情報 | 残す目的 |
|---|---|
| 現在の選択と、その理由 | 判断を理解してから変更できるようにする |
| 判断が成立する前提や、受け入れた制約 | 条件の違う場面に誤って適用することを防ぐ |
| 意味のある不採用案・失敗から得た知見 | 同じ調査や失敗を繰り返さないようにする |
| 判断の根拠となる検証条件・結果・限界 | 結果をどの範囲まで信頼できるか分かるようにする |
| 引き継ぐ必要がある問題と、再開の手掛かり | 作業報告を削除しても検討を再開できるようにする |

次の情報は、原則として作業報告に置きます。

- 今回の変更点、見え方の確認依頼、今回だけの動作確認。
- 作業時間、ツールの待機・再試行、作業中の経過。
- 後の判断に使わないスクリーンショットやログ。

単に過去に判断したという理由で、古い情報を残し続けません。後でも役立つ理由や知見は対応する話題に残し、役割を失った説明は削除します。過去の判断を別ファイルに保存することは標準にしません。

## 4. 見出しとラベル

### 見出しは話題にする

「判断」「理由」「未解決」の大きな章に多数の話題を混ぜず、「粒の大きさの基準」「RGBの配置」など、対象が分かる見出しにします。

その中でラベルを使い、必要な情報を拾いやすくします。ラベルだけを太字にし、本文は通常の文字にします。太字は情報の種類を見つけるために使い、重要度は言葉で示します。

### 共通ラベルの案

| ラベル | 設ける目的 | 読み取れること | 使う条件 |
|---|---|---|---|
| **方針** | 現在の選択を示し、説明の起点にする | 採用している方法、意図的に行わないこと | 現在の扱いを明示する意味がある |
| **理由** | 実装から分からない判断の根拠を残す | 目的、優先した条件、選択の根拠 | 後の判断に必要な理由がある |
| **検討案** | 再調査・再検討に使える比較を残す | 他に何を検討し、なぜ採用しなかったか | 独立して参照する意味がある比較がある |
| **確認結果** | 再利用する検証の根拠を示す | 確かめた条件・方法・結果・限界 | 今回だけの確認を超えて、判断の根拠になる |
| **未解決事項** | 問題を引き継げるようにする | 残っている問題、判断への影響、再開の手掛かり | 今後も検討する必要がある |

「方針・理由」を基本とし、残りは必要な場合に使う案です。すべての見出しに全項目を用意するルールにはしません。情報がなければ項目を省き、空欄や「該当なし」は作りません。

### 基本ラベルにしないもの

- **前提**：必要な条件は残すが、文書の冒頭や、対応する方針・理由に添える。
- **影響**：受け入れた欠点や制約は残すが、まず関連する方針・理由に含める。
- **未確認事項**：未確認という状態だけでは保存理由にしない。判断に影響する不確実さは、理由や未解決事項の中で明示する。
- **見直しの条件**：前提や理由を裏返しただけの項目は作らない。具体的な再検討のきっかけがある場合だけ、関連する説明に添える。

これらの情報を「理由」の長い段落に詰め込むことも避けます。独立して探す意味がある内容に育った場合は、項目や小見出しを追加できます。

### 追加・変更の基準

- 既存のラベルで表せる内容には、同じ意味の別名を追加しない。
- 新しいラベルは、読み手が独立して探す情報であり、既存のラベルと役割を区別できる場合に追加する。
- 一つの話題だけに必要なラベルを、すぐに共通ルールへ追加しない。繰り返し使う必要が出たときに検討する。
- 共通ルールには、名前だけでなく、目的・意味・使う条件・短い例を書く。
- ラベルを追加しただけでは過去の文書を一斉に書き換えない。通常の更新時に必要な範囲で揃える。

## 5. 設計文書の内容例

この章の設計内容・比較結果は、書き方を示すための架空例です。現在の実装の仕様や検証結果ではありません。例に登場する文書・画像も、将来の配置例です。

### `docs/design/crt-mask.md`

```markdown
# CRT mask

粒の大きさ、RGBの配置、縮小表示の扱いを変更するときに読む。
以下の比較は、同じ表示先の画面サイズを使うことを前提とする。

## 粒の大きさの基準

- **方針**：粒の大きさは、表示先のピクセルを基準にする。
- **理由**：入力画像の解像度が変わっても、同じ画面では
  粒の間隔を揃えたい。
- **検討案**：画像基準も試したが、画像の拡大率によって
  粒の間隔が変わるため採用しなかった。
- **確認結果**：解像度の異なる二つの画像を同じ画面サイズで
  表示し、粒の間隔が変わらないことを確認した。
  画面サイズを変えた場合の見え方は、この結果の範囲に含まない。

## RGBの配置

- **方針**：RGBの順序は固定し、切り替え設定は設けない。
- **理由**：現在は一種類の見え方を調整することが目的。
  配置を増やすと、調整と検証の組み合わせも増える。

## 縮小表示

- **方針**：当面は通常表示と同じマスクの強さを使う。
- **未解決事項**：縮小表示での文字の読みやすさは未確認。
  小さい文字を含む同じ画像でマスクの有無を比較し、
  縮小時に強さを下げる必要があるか判断する。
```

ここでは、粒の大きさには比較と検証を残し、RGBの配置には方針と理由だけを置いています。縮小表示の不確実さは、独立した「未確認」欄を作らず、検討を続ける問題として記載しています。

比較案が多い場合は、文章を繰り返すより表を使います。

```markdown
## 粒の大きさの基準

- **方針**：表示先のピクセルを基準にする。
- **理由**：入力画像を切り替えても粒の間隔を揃えるため。

### 検討案

| 案 | この用途での評価 | 扱い |
|---|---|---|
| 画像基準 | 画像の拡大率で粒の間隔が変わる | 不採用 |
| 表示先のピクセル基準 | 同じ画面では粒の間隔を揃えられる | 採用 |
```

短い情報はラベル付きの箇条書き、同じ軸で比較する情報は表、複雑な因果関係は項目の下の文章で説明します。

### 案内の例：`docs/design/README.md`

```markdown
# 設計の説明

変更したい内容に対応する文書から読む。

| 文書 | 扱う内容 |
|---|---|
| [CRT mask](crt-mask.md) | 粒の大きさ、RGBの配置、縮小表示 |
| [画面の拡大・縮小](display-scaling.md) | 表示倍率、余白、アスペクト比 |
```

案内には各文書の方針や理由をコピーしません。読む先を示す役割に絞ります。

### 分割後の例

サンプリングの説明が独立して読む内容に増えた場合は、`docs/design/crt-mask/sampling.md` に移します。`crt-mask.md` のファイル名は保ち、その話題の箇所を次の案内に置き換えます。

```markdown
## 入力画像のサンプリング

読み取り方の判断と比較は、[サンプリング](crt-mask/sampling.md)を参照。
```

移した説明を両方のファイルに残さないことで、更新する場所を一つにします。

## 6. 一時的な作業報告の内容例

以下の作業内容・時間・結果も架空例です。作業時間の表は、現行の報告項目を使っています。

作業報告の問題欄は、作業完了時点の記録です。引き継いだ問題の現在の状態は対応する設計文書で管理し、両方を同期して更新する運用にはしません。

配置例：`_temp/work-reports/2026-10-03_crt-mask/report.md`

```markdown
# CRT maskの粒の大きさを調整

入力画像を切り替えても、粒の間隔が変わらないようにした。

## 確認してほしいこと

- 画像を切り替えたとき、粒の大きさが不自然に変わらないか。
- 調整後の粒の大きさが、意図した見え方に合っているか。

[変更前後の比較画像](artifacts/comparison.png)

## 実施した確認

解像度の異なる二つの画像を、同じ画面サイズで表示した。
粒の間隔は変わらなかった。縮小表示での文字の読みやすさは
今回確認していない。

## 作業時間

| 工程 | 内容 | 未解決の問題 | 解決済みの問題 | 所要時間 |
|---|---|---|---|---|
| 比較 | 画像基準と画面基準を同じ表示条件で比較 | なし | 拡大率による違いを確認し、画面基準を選んだ | 12分 |
| 実装 | マスクの座標計算を変更 | なし | 入力画像による粒間隔の変化を解消 | 18分 |
| 検証 | 二つの画像で表示確認、比較画像を作成 | 縮小表示の読みやすさ | 通常表示では粒間隔が一定 | 15分（再実行待機4分を含む） |
| 文書整理 | 判断理由と引き継ぐ問題を記載 | なし | 作業報告を消しても必要な情報を読める | 5分 |

## 引き継ぎと整理

- 粒の大きさの判断理由と、縮小表示の問題は
  [CRT maskの説明](../../../docs/design/crt-mask.md)に記載した。
- 比較画像は今回の見え方の確認用で、現時点では長期保存しない。
- 見え方の確認が済み、比較画像の再利用も不要と確認できたら、
  この作業フォルダを手動で削除できる。
```

### 時間記録の粒度

- 固定された大きな工程名だけで区切らず、「二案を比較する」「座標計算を変更する」「三条件で表示を確認する」など、目的や対象が変わる単位で区切る。
- 目的の切り替わりで開始・終了を記録し、最後に所要時間をまとめる案とする。既存の記録から得られる時刻は利用し、ツール呼び出しごとの手動計測は要求しない。
- 通常の操作をすべて列挙せず、時間がかかった原因になる待機、再試行、範囲の拡大、同じ調査の繰り返しを補足する。
- 待機時間を内訳として書く場合、工程の時間に含まれることを明示し、合計で二重に数えない。
- 測定していない時間を実測値として埋めない。概算を使う場合は概算と書く。

記録から、何をどこまで行ったか、何が得られたか、どこで待機や手戻りが生じたかを読み取れることを目標とします。記録の細かさや計測手段の最終決定は、運用適用前の確認事項です。

## 7. AI向けの文書作成指示の例

指示は `docs/documentation.md` に集約する案です。人もAIも同じ基準を参照します。各指示を目的と作業の段階でまとめ、どの段階で問題が起きたかを確認できるようにします。

以下は、その文書に記載する指示の例です。

### 参照先を選ぶ

**目的**：関係する判断を確認し、既存の説明と重複・矛盾する記録を作らない。

- 作業に関係する話題の文書を参照する。案内がある場合は、そこから対象を選ぶ。
- 関係のない設計文書を毎回すべて読む必要はない。
- 文書と実装に食い違いがある場合は、どちらが現在の意図を表すか確認してから更新する。

**確認すること**：読むべき文書と、今回更新する場所が分かっている。

### 残す情報を選ぶ

**目的**：後の判断に役立つ情報を残し、作業の経過で文書を埋めない。

- 判断理由、重要な比較・失敗の知見、再利用する検証の根拠、引き継ぐ問題を選ぶ。
- 今回だけの確認依頼、経過、時間、資料は作業報告に置く。
- 役に立つことが何もなければ、新しい設計文書を作らない。

**確認すること**：残す情報ごとに、将来何に使うか説明できる。

### 設計の説明を更新する

**目的**：人が話題から情報を探し、現在の選択と理由を理解できるようにする。

- 話題を見出しにし、必要なラベルを使う。共通ラベルの意味はこの文書の定義に従う。
- 必要な条件や不確実さを明示する。空欄を埋めるために理由・比較案・検証結果を作らない。
- 長い説明は項目や小見出しで整理し、独立して読む意味がある部分だけ分割する。
- 同じ情報は一か所に置き、案内や関連文書からリンクする。
- 設計の説明から `_temp/` を参照しない。残す証拠が必要なら、残す領域へ移して参照する。

**確認すること**：作業報告を読まなくても、現在の判断、必要な根拠、引き継ぐ問題が分かる。

### 作業報告をまとめる

**目的**：作業直後の確認と、時間がかかった原因の調査に使えるようにする。

- 報告の冒頭に結果と確認してほしいことを置く。
- 作業時間は目的・対象が分かる単位でまとめ、重要な待機や手戻りを補足する。
- 継続して使う情報をどこへ記載したか、関連資料を何のために残しているかを書く。

**確認すること**：結果の確認方法、作業時間の内訳、残る問題、資料の用途が分かる。

### 一時資料を整理する

**目的**：必要な情報を失わず、用途の終わった資料を削除できるようにする。

- 継続して使う情報を記載し、引き継ぐ問題と必要な証拠が残っていることを確かめる。
- 作業報告を見なくても設計の説明が成立していることを確認する。
- 確認待ちの情報や資料の用途が残っていれば、作業フォルダを維持する。
- 整理条件が満たされた作業フォルダを手動で削除する。経過日数だけで削除しない。

**確認すること**：削除しても今後の作業に必要な情報が失われない。

指示を変更する際は、情報の選び方、書き方、参照先、時間記録、整理のうち、何がうまくいかなかったかを特定して対応する部分を変更します。書式だけの変更を理由に、過去の文書を一斉に書き換えません。

## 8. 適用する場合の作業範囲

1. ラベルの意味と運用、時間記録の粒度を最終確認する。
2. `docs/documentation.md` と作業報告のひな型を作る。
3. `AGENTS.md` の参照先と報告の保存先を更新する。
4. 既存文書から継続して使う情報を選び、話題ごとの文書へ整理する。新しい設計文書から参照できる状態を確認してから、重複した説明を削除する。
5. 既存の一時資料も、引き継ぎと用途を確認してから整理する。一括削除や日数による削除はしない。
6. 実際の作業で、探しにくい情報や記録負担を確認し、該当するルールを調整する。
7. 適用後は、この提案書と運用文書が重複した管理ルールにならないよう整理する。

本提案書の作成だけでは、これらの適用作業や既存文書の移動・削除は行いません。

### 適用前に確認すること

- 共通ラベルを上記の五つとし、そのうち方針・理由を基本とする案でよいか。
- 時間の記録方法と粒度が、原因の把握に役立ち、AIの記録負担も許容できるか。
- 既存の情報から何を残すか、どの話題にまとめるか。
