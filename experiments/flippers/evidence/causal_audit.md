# ③解除・再接触・通常接触の原因調査

2026-11-23 / Godot 4.7.2 stable official `ed1daf0bf` / `flipper`

本番コードは変更していない。調査用コードは `experiments/flippers/tests/causal_*.gd` に限定した。検出B、3条件の打球、新接触のみ法線分離、③、共有8接触を実験基準とし、改善処理は追加していない。**3条件と新接触法線分離は本番未反映**である。

結果は、A（解除時の仕様）だけでなく、B（分離後の状態分類）とC（標準接触の時刻・移動対象との整合性）の見直しが必要。Enemy側にも局所的な回復残りがあるが、群衆管理や物理全体の作り直しを必要とする根拠は得られていない。

## 1. 問題の発生条件

### 条件と比較方法

既存の近接Enemy84入力をそのまま使う。球半径24 px、Enemy半径30 px、球初速は下向き300 px/s、重力1,500 px/s²、上限3,600 px/s、60 Hz、両フリッパー入力を保持。各入力を60更新（1秒）追跡し、未解消の安全分離だけ従来どおり試行終了する。

`baseline` は「3条件＋新接触法線分離＋現行解除」、`unlimited` は同じ基準に前回の距離制限なし安全分離を使用する。後者は原因再現用であり採用案ではない。停止板はGodot、回転計画がある板はBで検出する。

更新順序はフリッパー計画・移動 → Enemy準備 → 集団処理（該当条件のみ）→ Enemy移動 → 球移動 → 退出処理。自動スポーン・ミサイル等は測定対象から外した。Enemyの経路を使わない旧84配置では、球から受けたノックバックによる移動は残す。実シーンのEnemy速度設定30 px/sを引き継ぎ、スクリプト既定値120 px/sと混同しない。

この比較では、右側面24.49 pxの重なりからの60.61 px上向き補正が、Enemyと壁を除いても残った。通常の球単体84入力で内部解除状態に至らなかったことと、内部に入った後の補正方針が適切であることは別問題である。

### ③を使わない通常接触

2種類の対照試験を分けた。

* **同一入力の③なし対照**：下向き300 px/s、フリッパーを含む形状・入力・更新順序を維持し、③だけ無効にした588試行。球＋板のみ／＋壁は各0/84打ち切り、Enemy 1体は移動・停止とも20/84、壁＋Enemy 1体20/84、壁＋3体38/84、全環境＋経路・群衆3体41/84。③がなくても反復問題は発生する。ただしフリッパー接触は含む。
* **フリッパーを除いた通常接触**：③と板への衝突を無効にし、球を上向き1,800 px/sでEnemyへ向ける504試行。Enemy単体、壁単体、壁＋Enemy 1体（移動／停止）は各0/84。壁＋群衆3体と全環境＋経路・群衆3体は各2/84で打ち切り。球・Enemy・壁だけでも同種の問題が発生する。初速が異なるため、前表との件数差を③の効果とは扱わない。

後者の4失敗条件では、同じ接触直前まで再生した後、Enemyの位置を保ったまま応答用表面速度だけ0にする対照と、Enemyを球の衝突照会から除く対照を作った。合計12試行で、各介入前状態が一致し、どちらの介入でも打ち切りが消えた。これは原因を調べる介入であり、Enemyの速度を0にしたり接触を無視したりする改善案ではない。

## 2. 原因の分類

### 確認できた原因

**(a) 復帰方向と候補の制約。** 側面24.49 pxを真上へ抜く既存方針が60.61 px補正を生む。16回の二分探索の丸め誤差ではない。距離制限なし安全分離では、近い法線方向をEnemyが塞ぐと、有限個の軸候補から249.01 px右移動等を選ぶ。Enemyを停止しても再現する。これは障害物配置と復帰方針の問題であり、Enemyが誤って動いたことを必要条件としない。

**(b) 完全分離後にも、更新開始の重なりを分離方針へ使い続ける。** 実験の `_initial_overlaps` は③解除前に保存され、その更新中は変わらない。安全分離で両板と周囲から0.03 px余裕付きで離れた後も `tick_initial_overlap=true` のまま。次の区間開始が非接触でも、独自接触は新接触法線分離を選べず上向きになる。これは実験上の分類の問題で、本番が既にこの分類を使っているという意味ではない。本番の独自分離はそもそも常に上向きである。

**(c) 共通移動の接触時刻にGodotの位置回復が混ざる。** `PinballMotion.advance_motion()` は `travel・motion / |motion|²` を経過割合として使う。しかしGodot 4.7.2の標準結果は、移動によるtravelに初期重なりの回復変位を加える。その投影を経過時間にすると、回復だけでも時間が進む。実装上の加算は [4.7.2のGodotSpace2D](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/modules/godot_physics_2d/godot_space_2d.cpp) の `test_body_motion()`、結果作成部分で確認した。

同じ移動開始変換・motion・margin0.03・回復報告trueを使う読み取り専用の `PhysicsServer2D.body_test_motion()` を追加照会した。10再現の72接触すべてで対象が一致し、照会なしの対照と更新終了位置・速度も一致した。停止板28.49 pxの例では、後続7接触のraw safe fractionがすべて0なのに、現行計算は合計約4.548 msを消費した。40.59 pxの例でも約3.212 ms。制限なし分離後のEnemy回復1回では約4.164 msだった。

したがって、以前の「接触時刻が変化した」という記録を、そのまま真の衝突時刻の進行と解釈してはいけない。今回の通常ログの `time_ms`／`remaining_ms` も**現行コードの推定値**で、訂正済みの物理時刻ではない。補正と移動を同じ時間として扱う問題は、独自接触との先後比較にも関係する。

なお [PhysicsBody2Dのラッパー](https://raw.githubusercontent.com/godotengine/godot/4.7.2-stable/scene/2d/physics/physics_body_2d.cpp) は浅い回復でtravelを投影し、remainderも書き換える。`get_remainder()` への単純置換だけで常に正しくなるとは提案しない。

**(d) 移動済みEnemyの形状と相対速度による応答が一致しない。** 通常接触の打ち切りで、標準判定はEnemyの更新後の位置に対して球の残り経路を止める。一方、`PinballBall._resolve_contact()` はEnemyの平均実移動速度を使い、相対的に離れていれば速度を変えない。同じ更新内の球の反復中にEnemy形状は進まないため、形状に対しては進めず、相対速度に対しては反射不要という状態を繰り返す。

代表例は球速度約(-944.95, -216.74)、Enemy速度約(-92.75, -532.82) px/s、相対法線成分+263.11 px/s（離れる向き）。8接触すべて速度変更0、球とEnemyの実際の食い込み深さも前後0で、Godotの余裕領域での接触が続き、推定残り15.520 msを捨てた。raw safe fractionは正の接触もあり、「全接触が初期重なりの回復だけ」という説明にはならない。時刻計算(c)と、この整合性(d)は別の問題である。

**(e) Enemy自身にも回復残りがある。** `Enemy.advance()` は要求移動が0でも標準回復を1回処理し、残りmotionが小さいと終了する。代表例では要求(0,0)、群衆なし、接触1回で約19.74 px移動した後、板への幾何的食い込み2.91 pxが残った。8回予算を使い切った例ではない。`velocity=(終了位置−開始位置)/delta` にはこの回復移動も含まれ、球の応答用表面速度へ渡る。

### まだ断定できないこと

* 更新順序を逆転すれば全問題が消えるとは未検証。同じ終点形状と相対速度の不一致は、単なる順番変更だけでは残り得る。
* Enemyの回復残りが、今回の全打ち切りの主因とは言えない。停止Enemyでも大補正が再現し、通常接触の反復は実食い込み0でも起きる。
* 5候補前後の安全分離で候補がないことは、任意方向・任意経路に安全位置が存在しない証明ではない。
* 群衆計算全体の破綻、Godot物理自体の不具合、接触上限8が不足していることは、今回の結果からは導けない。
* 60更新の観測は長時間プレイの発生率を示さない。今回は原因調査でありCPUの採否比較や見た目の許容判定は行っていない。

旧84配置との照合では、各入力の最大補正・打ち切り回数・未解消は一致し、新規干渉数も現行解除24／制限なし5イベントで一致した。一方、1秒後の位置は最大0.782／0.863 px一致しない。差が出始める更新を調べると、壁際の標準接触で速度は同じまま位置だけ約0.001〜0.003 px違い、その後拡大していた。元の継承 `_near_grid()` とEnemy処理を変更せずに再実行しても、旧保存値との終了位置差が出た（`causal_replay.json`）。観測版だけの挙動変更とは断定できず、接触回復の数値差が生じる詳細な理由は未確定。この長時間終了位置を同等性や方式採用の根拠には使わない。原因判定に使う90介入・12通常介入の直前状態、raw追加照会対照、4,644条件照合は別途所定の誤差内で一致した。

## 3. 関係する処理と再現例

### 実際の順序

| 段階 | 関係する関数 | 確認したこと |
| --- | --- | --- |
| 更新準備 | `main/main.gd:advance` | Enemyが球より先に移動する。球からのノックバックはEnemyの次回移動へ反映 |
| ③解除の判定 | `PinballMotion.advance` → `PinballFlippers.refresh_target` | 重力適用後に見込むy速度>1で解除。本番は内部位置の確認をしない |

| 対象の再有効化 | `PinballMotion.advance` の例外設定 | ③が解除されると両板除外を行わない。回転計画がある板は別途Godot照会から除外し、Bへ渡す |
| 検出・Godot回復 | `PinballMotion.advance_motion` | `move_and_collide(..., recovery_as_collision=true)` 内で回復と検出。回転計画ありはtest_only後にtravelを手動適用 |
| 独自分離 | `contact_separation` → `TableFlipper.separation_for` | 上向き探索16回。実験の新接触だけは法線へ置換。B/C/D分類は観測・実験側 |

| 残り移動 | `advance_motion` の同じループ | travel投影または独自hit.timeを差し引き、共有8回まで再検査。上限到達後の残りは移動しない |

Godot回復は、ユーザーコードが接触結果を受け取る前の移動照会内で行われる。`recovery_as_collision=false` は回復を止める設定ではなく、回復を接触として報告するかの設定である。今回このフラグは変更していない。

### 既存Enemy検証との関係

既存 `enemies/tests/enemy_test.gd` を変更せず再実行した結果は3,737検査中2失敗。観測ラッパーでも同じ2失敗だった。新しい調査コードの成功と混同しない。

* 経路退出を20秒以内に要求する検査：実シーンの速度30 px/sで、20秒後も経路途中を移動していた。別の元実装による1体・実経路・群衆あり追跡では33.15秒で退出した。直前の検査による盤面差もあるため軌道同一とは主張しないが、20秒の締め切り超過を経路停止の証拠にはできない。
* 小さいEnemyを高速板で内面に保持する検査：半径6 px、60°、1,440°/s、50 ms更新で板への深さ7.55 pxが残る。現行の18°・600°/s条件とは区別する。Enemyの終点姿勢に対する標準回復の限界を調べる局所課題であり、249 pxの球補正や群衆全体の問題を説明するものではない。

Enemyの観測版は既存 `advance()` の処理をそのまま写して履歴を付けた。4位置×4速度×3集団変位の48条件で元実装と比較し、位置差0.001 px未満・速度差0.01 px/s未満を確認した。これらは観測コードの同等性を確かめる数値で、ゲームの許容誤差を決めたものではない。

## 4. 改修すべき範囲

| 範囲 | 判断 | 理由 |
| --- | --- | --- |
| A：③解除の復帰 | 必要だが、ここだけでは不足 | 深い内部の解除方針は未決定。延期や候補内最短249 pxをそのまま採用できない |
| B：板の位置補正・再接触分類 | 優先して局所検証 | 完全分離しても履歴で上向き分離を選ぶ。実験分類を整理してから本番採用を判断 |
| C：共通反復・残り時間 | 見直しが必要 | Godot回復を経過時間へ含める計算と、移動済みEnemyに対する形状／応答の不一致を確認 |
| D：Enemy・壁・更新順序 | 限定範囲で検証 | Enemy実変位に回復が含まれる。Enemy局所の回復残りも存在。壁そのものの反射式が原因という証拠はない |
| E：物理・群衆管理の広範囲見直し | 現時点では不要 | 既知大補正は経路・群衆なしや停止Enemyで再現。Enemyの反復上限到達は0 |

Cを先送りしてAだけを複雑化すると、復帰直後は安全でも通常接触で再び止まる。逆にCの時刻を正しても、Bの大きな上向き補正は解決しない。それぞれ単独で比較すべきである。

## 5. 最小限の改善案（今回は未実装）

1. **分離済みという現在状態を、更新開始の履歴と分ける。** 対象板から完全に離れたことを確認した場合に限り、次区間の分離方針へ反映する。未解消の開始重なりは従来どおり別扱いし、履歴を一括削除しない。期待は17.20 pxで安全に復帰した後の25.73 px等の再補正を減らすこと。副作用は、本当の再進入・複数板接触を誤分類する可能性。法線方向へ0.239 px動けば他物体も安全になるとは未確認。
2. **標準判定の位置回復と移動時間を分ける。** 既存Bのhit.timeと比較する標準側時刻を、回復変位の投影から求めない。raw safe fraction等の明示値とラッパー後の位置変化を区別する薄い照会部品を実験する。期待は偽の時間消費・先後判定をなくすこと。副作用は従来隠れていたゼロ時間の反復が増える可能性。上限8を増やしたり、時間を架空に消費したりして隠さない。
3. **球と移動Enemyの照会・応答を同じ時刻の基準へそろえる。** まず既存Enemyの更新前後の記録を使う小さい実験とし、形状の時刻と応答用速度の契約をそろえる。静止壁・バンパーは既存処理を利用する。期待は食い込み0・速度変更0の連続停止を減らすこと。表面速度を一律0にするとノックバックや衝突威力が変わるため、その介入を採用実装にしない。更新順序変更だけ、または接触の単純無視で済むかは未確認。
4. **上記を測った後に③の復帰仕様を決める。** 現在の有限候補で塞がる理由を記録し、許容する復帰方向・変位をユーザーと確認する。無期限延期、距離無制限、安全位置探索の拡張は今回追加しない。局所修正で249 pxを必ず短縮できる保証はない。

Enemy自体の回復残りは別実験とし、必要なら要求移動0／高速板条件の扱いを確認する。球への共通移動部品の適用や群衆処理の作り直しまで広げない。
