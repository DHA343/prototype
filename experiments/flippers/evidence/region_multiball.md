# 中央を閉じた領域方式の検証

保存用の旧レポート。実装・シーン・旧テストは廃止済み。無効化は「打球した内部更新だけ」の1種類。現在の固定四角形の試験ではない。

## 条件

- 根元・先端のX座標は固定し、フリッパーの姿勢に応じたY座標だけを計算する。表示・打球面・領域も同じ上面を使う。
- 通常の 旧1球シーン の穴幅は84 pxで一定。20球の実験では左右の先端接点を同じ中央X座標に置き、穴幅0 pxにする。
- 左右は交差させない。高さが違う場合は中央の垂直境界でつなぎ、片側だけ上げても領域を閉じる。隠し底板は追加しない。
- 半径24 pxの球を20個、5列4段に配置。初速・位置を乱数シード1〜5で変更する。
- 両フリッパーを250 ms周期で操作し、最初の130 msは離し、その後120 msは押す。
- 各配置を物理時間8秒、外側の更新60 Hz、内部更新は最大1/240秒で動かす。
- 球同士は既存の試験用反射処理を使用する。同質量・反発係数0.8で、各球を順番に進める近似。
- 球を補充・退場させず、20球を最後まで動かす。

## 結果

| 配置 | 補正前に下へ出た球 | 補正後の禁止領域への残留 | 打球処理 | 最大の位置補正 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 0 / 20 | 0 | 205 | 26.01 px |
| 2 | 0 / 20 | 0 | 171 | 28.19 px |
| 3 | 0 / 20 | 0 | 216 | 21.30 px |
| 4 | 0 / 20 | 0 | 203 | 31.84 px |
| 5 | 0 / 20 | 0 | 183 | 51.75 px |

「補正前に下へ出た球」は、球全体が左右のフリッパー表示の下端より下へ出たかを位置補正前に記録する。球ごとに1回だけ数え、補正で内部へ戻っても記録を残す。深い食い込みすべてを数えるものではない。意図的に球を下へ配置する個別検査で、補正される前に検出できることも確認した。

「禁止領域への残留」は各内部更新の補正後の検査件数。0件は位置補正込みの結果で、途中に食い込みが発生しなかったという意味ではない。全5配置で球同士の衝突も発生した。

操作なしの20球・8秒でも、補正前の下への通過0球・禁止領域への残留0件。最大補正5.20 pxだった。

実行画面でも配置2の8秒再生を確認し、補正前の下への通過0球・禁止領域への残留0件だった。中央が閉じた色表示、片側だけ上げた際の中央の接続、初期化を確認し、実行時エラーは記録されなかった。

## 個別確認

- 通常の1球シーンで、左右を異なる周期で操作した90回の更新を検査。根元・先端のX座標は不変で、穴幅は84.000 pxだった。
- 通常の1球シーンでは、左右の不可視の出口壁への衝突と、中央通路からの正規の落下を確認した。
- 中央閉鎖シーンでは左右をそれぞれ上げた4姿勢で輪郭を検査。どの姿勢でも中央は閉じ、開放された落下口の辺は存在しなかった。
- 半径12・24・36 px、左右2か所の打点、3段階の埋まりを組み合わせた144件を検査。補正後は球全体が領域内に収まり、フリッパー上面側へ戻った。
- 上面に最初から接触する球は同じ内部更新で1回だけ打球され、約9.08 px移動した。次の内部更新では無効化が解除された。
- 盤面内の格子状の点・過去に内外誤判定が出た座標も再検査した。

## 残る問題

最大約52 pxの補正は残っている。配置5では上向きに打球された球に対し、約52 px上側へ戻す補正が発生した。通過を防げても、密集時の補正量が小さいとは限らない。

球同士などの接触処理が8回の上限に達した内部更新は、5配置でそれぞれ333・382・426・350・337件だった。残り時間の移動を保留する処理は今回変更していない。操作なしで密集させた場合も上限到達があり、密集時の接触処理には改善が必要。

同じ球が内部更新をまたいで再打球されることは許可している。打球処理回数を独立した返球回数とはみなさない。通常プレイでの発生率や負荷の比較は未計測。同じ乱数シードだけで実行環境をまたぐ完全な再現性は保証しない。

旧テストコードは整理時に削除済み。この資料は当時の条件と結果の保存記録として読む。

## 負荷の調査

実装を複製した一時的な計測用スクリプトで処理別の時間と呼び出し回数を調べ、別途、元の実装の更新時間も計測した。本体の挙動は変更していない。一時スクリプトは調査後に削除した。

元の実装をheadless・固定60 Hzで480回動かし、各回の更新と予測線計算のCPU時間を測定した。描画・エンジン側の残余処理・待機は含まない。実際の画面のフレーム時間やGPU時間とは異なる。

| 条件 | 平均 | 95パーセンタイル | 最大 |
| --- | ---: | ---: | ---: |
| 初期配置で停止・予測のみ | 0.38 ms | 0.43 ms | 0.55 ms |
| 20球・周期操作 | 6.22 ms | 8.09 ms | 11.30 ms |
| 20球・操作せず下部に密集 | 14.43 ms | 21.13 ms | 25.91 ms |

処理別の計測では、密集条件のCPU時間の約43%が `Region.first_contact()` 自身の処理だった。8秒間に168,950回呼ばれ、毎回49辺を走査する。密集時に接触処理が繰り返され、そのたびに全辺の線分・端点への衝突検査も再実行される。

内外判定も、球を進める前の補正確認、回転後の補正確認、補正後の検証で重複する。周期操作条件では `contains_ball()` が120,960回、補正前通過の検証用 `is_below_flippers()` が80,640回だった。後者は球ごとに左右の根元・先端の座標を計算し直すため、実際の衝突処理以外にも負荷を増やしていた。

色表示のCPU処理は周期操作条件の8秒全体で約19 ms、予測線計算は約119 msだった。同条件の更新＋予測の約5,190 msに対して小さく、今回のCPU計測では主因ではなかった。これらの処理別の値には計測用コードの負荷が含まれるため、上の元実装の時間と直接加算しない。

自動再生には別に0.5倍速の設定がある。見た目の半速と、CPU処理が間に合わないことは区別する。改善の優先対象は、近くない境界を衝突候補から外すこと、同一内部更新の座標・内外判定を再利用すること、密集時の接触処理の繰り返しを減らすこと。
